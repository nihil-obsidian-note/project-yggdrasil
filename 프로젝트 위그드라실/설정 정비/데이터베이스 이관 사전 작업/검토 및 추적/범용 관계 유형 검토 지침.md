# 범용 관계 유형 검토 지침

## 1. 목적

이 문서는 `프로젝트 위그드라실`의 설정·신격·비밀 설정 문서를 데이터베이스로 이관하기 전에 범용 문서 관계 유형을 검토하고 확정할 때 사용하는 실행 지침이다.

관계 설계의 출발점은 `프로젝트 위그드라실 문서 관계 설계 초안.md`이며, 초안을 그대로 확정하는 것이 아니라 현재까지의 확정 관계와 이관·추적 기록을 대조하여 세부 파트별 후보를 재구성한다.

## 2. 필수 참조 순서

범용 관계 유형의 새로운 세부 파트를 시작하거나 중단된 파트를 재개할 때에는 다음 순서를 지킨다.

1. `프로젝트 위그드라실 문서 관계 설계 초안.md`
2. 현재 파트보다 앞서 확정된 `2.x. 범용 관계 유형 - ... 확정본.md`
3. `2.5.1 괄호형 관계 분리 확정 갱신본.md`
4. `범용 관계 유형 검토·이관 추적 문서.md`
5. `데이터베이스 이관 사전 작업 정비.md`

첫 단계에서 반드시 설계 초안을 먼저 읽는다. 이관 목록만 보고 현재 파트의 범위를 새로 구성하거나, 모델의 일반 지식만으로 검토 후보를 먼저 만들지 않는다.

## 3. 세부 파트 검토 절차

각 세부 파트는 아래 순서로 진행한다.

### 3.1 설계 초안 분석

- 현재 세부 파트와 대응하는 초안의 관계군, 목적, 예시를 확인한다.
- 초안에 직접 관계군이 없으면 인접 관계군 사이에서 비어 있는 의미 영역을 분석한다.
- 초안은 출발점이며 확정본이 아니다.

### 3.2 기존 확정 관계 대조

- 이미 확정된 관계로 같은 의미를 표현할 수 있는지 먼저 확인한다.
- 관계명을 바꾸는 것만으로 중복 관계를 새로 만들지 않는다.
- 기존 관계의 대상 역할이나 3~4번째 선택 대상을 활용하면 표현 가능한 경우 재사용을 우선 검토한다.

### 3.3 이관·추적 내용 회수

- `범용 관계 유형 검토·이관 추적 문서.md`에서 현재 파트로 넘겨진 모든 후보를 회수한다.
- 이관 후보는 자동 확정하지 않는다.
- 최초 위치, 이관 이유, 당시 미결 쟁점을 함께 검토한다.

### 3.4 검토 대상 전체 리스트업

세부 파트를 하나의 단위로 보고 검토 대상을 한 번에 제시한다. 한 관계씩 먼저 확정한 뒤 다음 후보로 넘어가지 않는다.

기본 양식은 다음과 같다.

| 정방향 | 역방향 | 방향 | 대상 수 | 대상 역할 | 템플릿 | 1차 판정 |
| --- | --- | --- | ---: | --- | --- | --- |
| 예시 관계함 | 예시 관계당함 | 방향 | 2~3 | 행위 주체 / 행위 대상 / 관련 사건(선택) | `{행위 주체}{이/가} {행위 대상}{을/를} {관계} ({관련 사건})` | 검토 |

- `정방향`, `역방향`: 실제 UI 표시 관계명 후보를 적는다.
- `방향`: `방향` 또는 `대칭`으로 판정한다.
- `대상 수`: 최소 2개, 최대 4개 범위에서 적는다.
- `대상 역할`: 숫자 슬롯이 아니라 의미 역할명으로 적는다.
- 선택 대상은 역할명 뒤에 `(선택)`을 붙인다.
- `템플릿`: 의미 역할명 치환자를 사용한다.
- `1차 판정`: `유지`, `신규 후보`, `재사용 검토`, `통합 검토`, `이관 검토`, `제외 검토`, `괄호형 검토` 등을 사용한다.

리스트업 단계는 확정 단계가 아니다. 검토 중 후보 수가 늘거나 줄어드는 것을 정상으로 본다.

### 3.5 파트 전체 정밀 검토

리스트에 올라온 모든 후보를 한 번에 비교한다.

각 후보는 다음 항목을 확인한다.

- 기존 확정 관계와 의미가 중복되는가.
- 동일 파트 후보끼리 의미 범위가 겹치는가.
- 다른 후속 파트에서 다루는 편이 더 자연스러운가.
- 독립 relation type으로 검색·선택할 실익이 있는가.
- 관계 자체가 아니라 사건 설명이나 보조 속성으로 충분한가.
- 정방향과 역방향이 자연스러운가.
- 대칭 관계가 더 적절한가.
- 2~4개의 대상 역할이 실제 설정 사실을 손실 없이 표현하는가.
- 괄호형 독립 관계로 분리할 가치가 있는가.

검토 결과는 `확정`, `재사용`, `통합`, `이관`, `제외`, `괄호형 독립 관계` 가운데 하나로 정리한다. 필요하면 검토 도중 새로운 후보를 추가한다.

## 4. 괄호형 독립 관계 규칙

### 4.1 기본 원칙

괄호형 관계명은 표시용 별칭이 아니라 데이터베이스에 별도 ID로 등록되는 독립 `relation type`이다.

예:

- `증언함(목격)`
- `증언함(전언)`
- `희생됨(전투)`
- `회수함(유해)`

같은 기본 관계에서 파생되어도 각 괄호형 관계는 서로 다른 relation type ID를 가진다.

### 4.2 반드시 검토할 세 가지 표현 방식

모든 후보는 다음 세 가지 중 어느 방식이 적절한지 검토한다.

1. **일반 관계**: `공격함`
2. **괄호형 독립 관계**: `공격함(기습)`
3. **보조 속성**: `공격함` 관계의 방식=`기습`

괄호형 검토를 생략하고 바로 보조 속성으로 처리해서는 안 된다. 반대로 세부 표현이 있다는 이유만으로 모두 괄호형 관계로 만들지도 않는다.

### 4.3 괄호형으로 분리하는 기준

다음 조건을 충족할수록 괄호형 독립 관계로 분리한다.

- 사용자가 관계 생성 화면에서 해당 세부 의미를 직접 선택할 가치가 있다.
- 세부 유형 자체로 검색·필터링·역추적할 필요가 있다.
- 일반 관계와 구별되는 설정상 의미가 반복적으로 발생한다.
- 단순한 수단·장소·시점·강도 이상의 의미 차이가 있다.
- 정방향·역방향 표시에서도 세부 의미를 보존하는 편이 자연스럽다.

다음은 보조 속성 쪽을 우선한다.

- 일회적인 전술 방식이나 상황 설명이다.
- 자유로운 종류가 지나치게 많아 relation type을 무한히 늘릴 가능성이 있다.
- 검색·선택 단위로 분리할 실익이 적다.
- 기본 관계와 의미적 차이가 거의 없고 방식만 달라진다.

### 4.4 일반 관계와의 병존

괄호형 관계가 존재해도 일반 관계를 자동 삭제하지 않는다. 일반 관계와 세부 관계를 모두 사용할 필요가 있으면 병존시킨다.

예를 들어 일반 `증언함`과 `증언함(목격)`, `증언함(전언)`은 각각 독립적으로 존재할 수 있다.

### 4.5 표기 주의

대상 역할의 `(선택)` 표기는 괄호형 relation type과 다른 문법이다.

- `관련 사건(선택)`: 대상 역할이 선택 사항이라는 표시
- `증언함(목격)`: 관계명 자체에 포함된 세부 유형

둘을 혼동하지 않는다.

## 5. 사용자 확정과 다음 파트 이동

- 세부 파트 전체 검토 결과를 제시한 뒤 사용자 확정을 받는다.
- 사용자가 확정하면 그 파트의 관계 수와 이관·재사용·제외 결과를 즉시 진행 상태에 반영한다.
- 확정되지 않은 파트를 완료로 기록하지 않는다.
- 미결 사항이 있으면 다음 파트로 넘어가기 전에 해당 미결을 별도로 점검한다.
- 미결이 해소되고 사용자가 확정하면 다음 세부 파트로 이동한다.

## 6. 추적 문서 갱신 규칙

사용자 확정 후 `범용 관계 유형 검토·이관 추적 문서.md`에 다음을 반영한다.

- 새로 확정된 관계
- 기존 관계 재사용 판정
- 다른 관계에 통합된 후보
- 후속 파트로 이관된 후보와 이관 이유
- 제외된 후보
- 새로 추가된 괄호형 독립 relation type
- 남아 있는 미결 사항

이관된 후보를 원래 위치와 후속 위치 양쪽에서 미처리 상태로 중복 추적하지 않는다.

## 7. 금지 사항

- 설계 초안을 확인하지 않고 이관 목록만으로 파트를 구성하지 않는다.
- 한 관계씩 개별 확정하여 파트 전체 비교를 방해하지 않는다.
- 리스트업 단계의 후보를 확정 관계처럼 기록하지 않는다.
- 기존 관계로 표현 가능한 의미를 명칭 차이만으로 중복 생성하지 않는다.
- 괄호형 관계를 단순 표시 별칭이나 자유 입력값으로 취급하지 않는다.
- 괄호형 검토 없이 세부 의미를 자동으로 보조 속성 처리하지 않는다.
- 자연스럽지 않은 역관계명을 형식적으로 만들지 않는다.
- 사용자 확정 전에 추적 문서의 상태를 `확정`으로 바꾸지 않는다.
