# DB 이관 기본 기능 명세 초안

## 1. 문서 목적

이 문서는 설정 문서 관리 시스템의 DB 이관을 위한 기본 기능 범위와 후속 기능 범위를 기록한다. 현재 확정된 기능만 정리하며, 세부 테이블·컬럼·API 설계는 후속 DB 설계에서 확정한다.

## 2. 전 테이블 공통 컬럼

모든 테이블은 다음 기본 컬럼을 가진다.

```text
id
useYn
delYn
createDate
updateDate
deleteDate
```

- `id`는 자동 증가 숫자형 PK를 사용한다.
- 모든 삭제는 소프트 삭제로 처리한다.
- 삭제 시 `delYn = Y`, `deleteDate = 삭제 시각`으로 기록한다.
- 비활성화는 `useYn = N`이며 삭제와 구분한다.
- 기본 조회 대상은 `useYn = Y AND delYn = N`이다.
- 매핑·관계·리비전 등 모든 테이블에도 같은 기본 컬럼을 적용한다.
- 동일 범위에 같은 이름의 활성 데이터가 있으면 중복 생성을 차단한다.
- 동일 범위에 같은 이름의 소프트 삭제 데이터가 있으면 별도 안내 없이 기존 행을 자동 복구한다.
- 자동 복구 시 기존 `id`와 내용·하위 데이터·매핑을 유지하고 `delYn = N`, `deleteDate = null`로 변경한다.

## 3. 관리자와 접근 권한

### 3.1 관리자 등급

- `SUPER_ADMIN`: 시스템 전체에서 단 한 명만 존재하며 마스터 계정이다.
- `ADMIN`: 슈퍼 어드민이 생성한다.
- `SUB_ADMIN`: 어드민이 생성한다.
- 모든 관리자 등급은 `admins` 단일 테이블에서 관리한다.
- 로그인 식별자는 이메일이며 이메일은 전역에서 중복될 수 없다.
- 인증에는 이메일·비밀번호와 JWT를 사용한다.
- 비밀번호 원문은 저장하지 않고 안전한 해시만 저장한다.
- 계정 생성 시 시스템이 임시 비밀번호를 만들고 해당 이메일로 발송한다.
- 최초 로그인에서는 비밀번호 변경 기능만 사용할 수 있다.
- 비밀번호를 변경하기 전에는 다른 시스템 기능을 사용할 수 없다.
- 비밀번호 변경 완료 후 정상 JWT를 발급한다.

### 3.2 프로젝트 권한

- 슈퍼 어드민은 모든 계정과 프로젝트를 조회·관리할 수 있다.
- 어드민은 여러 프로젝트를 생성할 수 있다.
- 프로젝트마다 소유 어드민은 정확히 한 명이다.
- 어드민은 자신이 생성한 프로젝트만 조회·관리·삭제할 수 있다.
- 다른 어드민의 프로젝트는 목록·검색·직접 URL·API에서 보이지 않는다.
- 서브 어드민은 프로젝트를 생성하거나 삭제할 수 없다.
- 프로젝트에는 여러 서브 어드민을 초대할 수 있다.
- 이미 생성된 서브 어드민은 자신을 생성한 어드민의 다른 프로젝트에도 초대할 수 있다.
- 서브 어드민은 초대된 프로젝트만 조회·관리할 수 있다.
- 서브 어드민은 프로젝트 안의 카테고리·템플릿·문서를 삭제할 수 있다.
- 서브 어드민의 관리 범위는 문서·카테고리·템플릿의 조회·생성·수정·삭제로 한정한다.
- 서브 어드민은 프로젝트·월드·계정·관계 유형·관계 설정을 관리할 수 없다.
- 서브 어드민 프로젝트 배정 매핑의 테이블명은 `projectAdmins`를 사용한다.

## 4. 기본 데이터 계층

```text
ADMIN
└─ PROJECT
   └─ WORLD
      ├─ CATEGORY
      ├─ TEMPLATE
      └─ DOCUMENT
```

- 어드민은 프로젝트를 생성한다.
- 프로젝트 안에는 여러 월드를 생성할 수 있다.
- 월드 안에는 카테고리·템플릿·문서를 생성할 수 있다.
- 프로젝트를 삭제해도 하위 데이터에 삭제 상태를 연쇄 적용하지 않는다.
- 삭제된 프로젝트의 하위 데이터는 UI와 API에서 접근을 차단한다.
- 프로젝트를 복구하면 기존 하위 데이터와 권한 구성을 다시 사용할 수 있다.

## 5. 카테고리

- 카테고리와 서브카테고리는 하나의 `categories` 테이블을 공유한다.
- 자기참조 외래키 `upperCategoryId`로 상하위 구조를 표현한다.
- 최상위 카테고리는 `upperCategoryId = null`이다.
- 카테고리 깊이는 최대 3단계다.
- 생성·이동 결과가 4단계 이상이면 서버에서 차단한다.
- 상위·하위 카테고리는 반드시 같은 월드에 속해야 한다.

## 6. 템플릿과 카테고리

- 하나의 메인 카테고리는 하나의 템플릿만 선택할 수 있다.
- 하나의 템플릿은 여러 메인 카테고리에 적용될 수 있다.
- 템플릿 미할당 상태를 허용하며 이때 `templateId = null`이다.
- 템플릿은 상속되지 않는다.
- 템플릿은 1단계 메인 카테고리에만 할당할 수 있다.
- 2·3단계 서브카테고리에는 템플릿을 할당할 수 없다.
- 카테고리 상세 페이지에서 템플릿을 할당할 수 있다.
- 템플릿 상세 페이지에서 여러 메인 카테고리를 일괄 할당할 수 있다.
- 카테고리와 템플릿은 반드시 같은 월드에 속해야 한다.

## 7. 문서와 카테고리 경로

- 문서당 메인 카테고리는 반드시 하나다.
- 문서는 메인 카테고리 아래에 선택적으로 2·3단계 카테고리를 가질 수 있다.
- 문서는 최하위 카테고리에만 소속되는 것이 아니라 선택한 카테고리 경로 전체와 매핑된다.
- 문서당 카테고리 매핑은 최대 3개다.
- 연결된 카테고리는 하나의 연속된 상하위 경로여야 한다.
- 서로 다른 메인 카테고리 경로를 동시에 가질 수 없다.
- 3단계를 선택하려면 1·2단계가 모두 존재해야 한다.
- 문서의 템플릿은 1단계 메인 카테고리에서 결정된다.

## 8. 템플릿 섹션과 문서 본문

### 8.1 섹션 메타데이터

- 섹션은 DB에서 관리한다.
- 섹션은 고유 ID, 제목, 순서, 레벨을 가진다.
- 같은 섹션 ID는 같은 섹션을 의미한다.
- 섹션 데이터에는 문서 내용을 저장하지 않는다.
- 섹션 제목은 템플릿 구성 요소이므로 문서 작성·수정 화면에서 변경할 수 없다.
- 문서에서 하위 섹션을 자율적으로 추가할 수 있다.
- 하위 섹션도 DB에서 제목·순서·레벨·상위 섹션 관계를 관리한다.
- 문서에서 만든 섹션은 해당 문서에만 귀속되며 템플릿 섹션으로 승격할 수 없다.
- 같은 구조가 템플릿에도 필요하면 템플릿 편집 화면에서 별도 섹션으로 생성한다.

### 8.2 Markdown 본문

- 문서 본문의 유일한 영구 정본은 `documents.content`다.
- `documents.content`에는 Markdown 문자열만 저장한다.
- 문서를 로드하면 템플릿과 문서 섹션 데이터를 기준으로 Markdown을 `#`, `##`, `###` 단위로 분리한다.
- 분리된 섹션별 내용은 화면의 임시 스토어 데이터로만 사용한다.
- 작성·수정 화면에는 섹션 수만큼 Markdown textarea를 표시한다.
- 섹션 제목은 고정 UI로 표시하고 textarea에는 해당 섹션의 본문만 입력한다.
- 저장 시 섹션 제목·레벨·순서와 임시 스토어 내용을 다시 Markdown 문자열로 결합하여 `documents.content`에 저장한다.
- 문서 섹션 매핑에는 콘텐츠를 저장하지 않는다.

### 8.3 템플릿 버전과 문서 갱신

- 템플릿은 버전을 가진다.
- 템플릿 섹션의 구성·제목·순서·레벨이 변경되면 버전을 증가시킨다.
- 문서는 마지막으로 적용한 템플릿 버전을 기록한다.
- 문서 적용 버전이 현재 템플릿 버전보다 낮으면 구버전 템플릿 경고를 표시한다.
- 템플릿 변경은 기존 문서에 자동 반영하지 않는다.
- 사용자가 템플릿 갱신 기능을 실행했을 때만 최신 구조를 적용한다.
- 동일 섹션 ID의 기존 본문은 보존하고 신규 섹션은 빈 본문으로 추가한다.
- 제목·레벨·순서 변경은 최신 템플릿 구조를 적용한다.
- 템플릿에서 삭제된 섹션과 기존 본문은 자동 삭제하지 않고 삭제된 템플릿 섹션으로 경고 표시한다.
- 새 문서에는 삭제된 템플릿 섹션을 적용하지 않는다.

## 9. 관계 유형

### 9.1 관계 유형 구분

- 시스템이 제공하는 기본 관계가 존재한다.
- 어드민이 만드는 사용자 정의 관계가 존재한다.
- 현재 검토 완료된 COMMON 관계는 시스템 기본 관계 데이터로 사용한다.
- 룩스테라·엘드로스 전용 확장 관계는 마스터가 사용하는 사용자 정의 관계 데이터다.
- 다른 어드민은 자신의 용도에 맞는 관계를 자유롭게 생성할 수 있다.
- 사용자 정의 관계는 생성한 어드민에게 귀속된다.
- 어드민이 한 번 만든 사용자 정의 관계는 자신이 소유한 여러 프로젝트와 월드에서 재사용할 수 있다.
- 다른 어드민의 사용자 정의 관계는 조회하거나 사용할 수 없다.

### 9.2 월드별 관계 활성화

- 관계 정의와 월드별 적용 설정을 분리한다.
- 월드에서 관계를 사용하려면 해당 관계를 활성화해야 한다.
- 관계 역할별 허용 카테고리는 월드마다 별도로 할당한다.
- 같은 관계라도 월드마다 다른 카테고리 구성을 가질 수 있다.
- 카테고리가 설정되지 않은 관계는 문서 관계 선택지에 표시하지 않는다.
- UI뿐 아니라 API에서도 같은 활성화·카테고리 조건을 검증한다.
- 기존 관계의 카테고리 할당을 해제해도 이미 생성된 관계 인스턴스는 보존한다.

### 9.3 대상 수와 역할 슬롯

- 관계 유형은 최소 대상 수와 최대 대상 수를 가진다.
- 역할 슬롯은 필수 또는 선택으로 구분할 수 있다.
- 역할 슬롯의 필수 여부는 `requiredYn`으로 명시한다.
- 필수 역할은 모두 카테고리가 할당되어야 한다.
- 사용 가능한 역할 수가 최소 대상 수 이상이어야 관계가 선택지에 표시된다.
- 선택 역할은 카테고리가 할당된 경우에만 실제 대상을 배정할 수 있다.
- 관계 인스턴스의 역할 슬롯 하나에는 문서 하나만 배정한다.
- 활성 데이터 기준 `relationshipId + relationshipTypeRoleId` 조합은 유일해야 한다.
- 여러 대상 문서는 같은 관계 인스턴스 ID를 공유한다.
- 화면에서는 같은 관계 ID의 역할과 대상 문서를 한 묶음으로 표시한다.
- 서로 다른 월드의 문서끼리는 관계를 생성할 수 없다.
- 관계 역할에 할당된 카테고리가 문서의 최대 3단계 카테고리 경로 중 하나와 일치하면 해당 역할에 문서를 배정할 수 있다.
- 참·거짓 상태 컬럼은 `requiredYn`, `systemYn`, `passwordChangeRequiredYn`처럼 `Yn` 접미사를 사용한다.

## 10. 초기 구현 범위

초기 구현에는 다음 기능을 포함한다.

- 슈퍼 어드민·어드민·서브 어드민
- 프로젝트·월드
- 최대 3단계 카테고리
- 템플릿·섹션
- Markdown 문서 작성·수정
- 섹션 단위 편집과 Markdown 재조립
- 기본 관계·사용자 정의 관계
- 월드별 관계 활성화와 역할별 카테고리 할당
- 다항 문서 관계
- 전 테이블 공통 컬럼과 소프트 삭제

## 11. 후속 위키 기능: 리비전

리비전은 초기 구현에서 제외하고 위키 기능 구현 단계에서 추가한다.

- 자동 저장은 사용하지 않는다.
- 사용자가 명시적으로 저장 버튼을 클릭했을 때만 저장을 판정한다.
- 현재 연결된 리비전 내용과 제출된 `documents.content`가 다를 때만 신규 리비전을 생성한다.
- 리비전에 저장하는 내용은 `documents.content`의 Markdown 본문뿐이다.
- 리비전 ID는 자동 증가 숫자형 PK다.
- 문서와 현재 리비전은 별도 매핑으로 관리한다.
- 과거 리비전 복원은 현재 리비전 매핑 ID를 변경하는 방식이다.
- 복원 자체로 신규 리비전을 만들지 않는다.
- 복원 후 내용을 수정하여 저장하면 그 시점에 신규 리비전을 생성한다.
- 리비전 판단에서 가장 우선하는 행위는 명시적인 저장이다.

## 12. 별도 장기 보류: 일반 사용자와 토론장

토론장은 리비전과 별개의 장기 보류 기능이다.

- 미래에는 일반 사용자 계정이 추가될 수 있다.
- 모든 문서는 토론장을 가질 수 있다.
- 토론장은 여러 댓글로 구성된다.
- 댓글에는 답글을 작성할 수 있다.
- 일반 사용자·토론장·댓글·답글의 권한과 테이블은 후속 별도 설계에서 결정한다.
- 초기 구현과 위키 리비전 구현 범위에는 포함하지 않는다.

## 13. 후속 설계 대상

- 정확한 테이블 목록과 외래키
