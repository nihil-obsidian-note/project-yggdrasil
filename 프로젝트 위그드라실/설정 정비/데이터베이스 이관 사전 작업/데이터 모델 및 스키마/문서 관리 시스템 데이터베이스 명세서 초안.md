# 문서 관리 시스템 데이터베이스 명세서 초안

## 1. 목적과 범위

문서 관리 시스템 초기 구현에 필요한 데이터베이스 구조를 정의한다. 초기 범위는 관리자 인증, 프로젝트, 월드, 카테고리, 템플릿, 섹션, Markdown 문서, 기본·사용자 정의 관계와 실제 문서 관계다.

초기 범위에서 문서 리비전, 일반 사용자, 토론장, 댓글·답글은 제외한다. 문서 전용 섹션은 템플릿 섹션으로 승격하지 않는다.

## 2. 공통 규칙

### 2.1 명명

- 테이블명은 복수형 camelCase를 사용한다.
- 컬럼명은 camelCase를 사용한다.
- PK는 `id`, FK는 `<대상명>Id` 형식을 사용한다.
- 불리언 상태는 `Yn`, 날짜는 `Date` 접미사를 사용한다.

### 2.2 전 테이블 공통 컬럼

| 컬럼 | 타입 | NULL | 기본값 | 설명 |
|---|---|:---:|---|---|
| `id` | BIGINT | N | AUTO_INCREMENT | PK |
| `useYn` | CHAR(1) | N | `Y` | 사용 여부 |
| `delYn` | CHAR(1) | N | `N` | 삭제 여부 |
| `createDate` | DATETIME | N | CURRENT_TIMESTAMP | 생성 시각 |
| `updateDate` | DATETIME | N | CURRENT_TIMESTAMP | 수정 시각 |
| `deleteDate` | DATETIME | Y | NULL | 삭제 시각 |

모든 YN 컬럼은 `Y`, `N`만 허용한다. 모든 삭제는 소프트 삭제이며 물리 연쇄 삭제를 사용하지 않는다.

상위 데이터 삭제 시 하위 행의 `delYn`은 변경하지 않고 UI·API 접근만 차단한다. 상위 복구 시 기존 하위 데이터와 매핑을 다시 사용한다.

동일 범위·동일 이름의 활성 행이 있으면 중복 오류를 반환한다. 삭제 행이 있으면 안내 없이 기존 행을 복구하며 ID·내용·하위 데이터·매핑을 유지하고 `delYn = N`, `deleteDate = NULL`로 변경한다.

## 3. 테이블 명세

## 3.1 `admins`

모든 관리자 계정을 관리한다.

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `email` | VARCHAR(320) | N | UK | 로그인 이메일 |
| `passwordHash` | VARCHAR(255) | N |  | 비밀번호 해시 |
| `name` | VARCHAR(100) | N |  | 표시명 |
| `role` | VARCHAR(20) | N | IDX | `SUPER_ADMIN`, `ADMIN`, `SUB_ADMIN` |
| `createdByAdminId` | BIGINT | Y | FK | 생성 관리자 |
| `passwordChangeRequiredYn` | CHAR(1) | N |  | 비밀번호 변경 필요 |
| `lastLoginDate` | DATETIME | Y |  | 마지막 로그인 |

- 이메일은 삭제 여부와 관계없이 전역 유일하다.
- 슈퍼 어드민은 활성 상태 한 명만 허용하며 생성자는 NULL이다.
- ADMIN 생성자는 SUPER_ADMIN, SUB_ADMIN 생성자는 ADMIN이어야 한다.
- 임시 비밀번호 변경 전에는 비밀번호 변경 기능만 사용할 수 있다.

인덱스: `UNIQUE(email)`, `INDEX(role)`, `INDEX(createdByAdminId)`.

## 3.2 `adminRefreshTokens`

JWT 리프레시 토큰을 관리한다.

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `adminId` | BIGINT | N | FK | 토큰 소유 관리자 |
| `tokenHash` | VARCHAR(255) | N | UK | 토큰 해시 |
| `expiresDate` | DATETIME | N | IDX | 만료 시각 |
| `revokedYn` | CHAR(1) | N |  | 폐기 여부 |
| `revokedDate` | DATETIME | Y |  | 폐기 시각 |
| `deviceInfo` | VARCHAR(500) | Y |  | 접속 환경 |

- 액세스 토큰과 리프레시 토큰 원문은 저장하지 않는다.
- 로그아웃·비밀번호 변경·계정 비활성화 시 관련 토큰을 폐기한다.

## 3.3 `projects`

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `adminId` | BIGINT | N | FK | 단일 소유 ADMIN |
| `name` | VARCHAR(200) | N |  | 프로젝트명 |
| `description` | TEXT | Y |  | 설명 |

- 소유자는 ADMIN만 가능하다.
- ADMIN은 여러 프로젝트를 만들 수 있다.
- `UNIQUE(adminId, name)`.
- 다른 ADMIN의 프로젝트는 존재 여부도 노출하지 않는다.

## 3.4 `projectAdmins`

프로젝트에 배정된 SUB_ADMIN을 관리한다.

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `projectId` | BIGINT | N | FK | 프로젝트 |
| `adminId` | BIGINT | N | FK | SUB_ADMIN |

- `UNIQUE(projectId, adminId)`.
- 프로젝트 소유자와 SUB_ADMIN 생성자는 같아야 한다.
- 같은 SUB_ADMIN을 동일 소유자의 여러 프로젝트에 배정할 수 있다.

## 3.5 `worlds`

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `projectId` | BIGINT | N | FK | 프로젝트 |
| `name` | VARCHAR(200) | N |  | 월드명 |
| `description` | TEXT | Y |  | 설명 |

- `UNIQUE(projectId, name)`.
- SUB_ADMIN은 월드를 관리할 수 없다.

## 3.6 `categories`

최대 3단계 카테고리를 자기참조 구조로 관리한다.

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `worldId` | BIGINT | N | FK | 월드 |
| `upperCategoryId` | BIGINT | Y | FK | 상위 카테고리 |
| `templateId` | BIGINT | Y | FK | 메인 카테고리 템플릿 |
| `name` | VARCHAR(200) | N |  | 카테고리명 |
| `level` | TINYINT | N | IDX | 1~3 |
| `order` | INT | N | IDX | 출력 순서 |

- 1단계는 상위가 NULL이며 템플릿을 할당할 수 있다.
- 2·3단계는 바로 위 단계 카테고리를 참조하며 템플릿을 가질 수 없다.
- 상하위 카테고리와 템플릿은 같은 월드에 속해야 한다.
- `UNIQUE(worldId, COALESCE(upperCategoryId, 0), name)`.

## 3.7 `templates`

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `worldId` | BIGINT | N | FK | 월드 |
| `name` | VARCHAR(200) | N |  | 템플릿명 |
| `description` | TEXT | Y |  | 설명 |
| `version` | INT | N |  | 현재 버전, 기본 1 |

- `UNIQUE(worldId, name)`.
- 섹션 구성·제목·레벨·순서 변경 시 버전을 증가시킨다.
- 기존 문서는 자동 갱신하지 않는다.

## 3.8 `sections`

섹션 메타데이터만 관리하며 본문은 저장하지 않는다.

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `title` | VARCHAR(300) | N |  | 제목 |
| `level` | TINYINT | N |  | Markdown H1~H6 |
| `sectionType` | VARCHAR(20) | N | IDX | `TEMPLATE`, `DOCUMENT` |
| `createdByAdminId` | BIGINT | N | FK | 생성 관리자 |

- 문서 전용 섹션은 해당 문서에서만 사용하고 템플릿으로 승격하지 않는다.
- 섹션 제목은 문서 편집 화면에서 변경할 수 없다.

## 3.9 `templateSections`

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `templateId` | BIGINT | N | FK | 템플릿 |
| `sectionId` | BIGINT | N | FK | TEMPLATE 섹션 |
| `upperSectionId` | BIGINT | Y | FK | 상위 섹션 |
| `order` | INT | N | IDX | 순서 |
| `requiredYn` | CHAR(1) | N |  | 필수 여부 |

- `UNIQUE(templateId, sectionId)`.
- 상위 섹션은 같은 템플릿에 속해야 한다.
- 삭제된 섹션은 신규 문서에 적용하지 않지만 기존 문서에서는 본문과 함께 보존하고 경고한다.

## 3.10 `documents`

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `worldId` | BIGINT | N | FK | 월드 |
| `templateId` | BIGINT | Y | FK | 적용 템플릿 |
| `templateVersion` | INT | Y |  | 마지막 적용 버전 |
| `title` | VARCHAR(300) | N |  | 제목 |
| `content` | LONGTEXT | N |  | Markdown 전체 본문 |

- `UNIQUE(worldId, title)`.
- `content`가 본문의 유일한 영구 정본이다.
- 섹션별 콘텐츠는 다른 테이블에 저장하지 않는다.
- 적용 버전이 최신 버전보다 낮으면 구버전 경고를 표시한다.
- 사용자가 템플릿 갱신을 실행한 경우에만 구조를 갱신한다.

## 3.11 `documentCategories`

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `documentId` | BIGINT | N | FK | 문서 |
| `categoryId` | BIGINT | N | FK | 카테고리 |
| `level` | TINYINT | N | IDX | 1~3 |

- `UNIQUE(documentId, level)`, `UNIQUE(documentId, categoryId)`.
- 1단계는 필수이며 2·3단계는 선택이다.
- 연결 카테고리는 같은 월드의 연속된 단일 경로여야 한다.

## 3.12 `documentSections`

문서의 실제 섹션 구조만 관리하고 콘텐츠는 저장하지 않는다.

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `documentId` | BIGINT | N | FK | 문서 |
| `sectionId` | BIGINT | N | FK | 섹션 |
| `upperSectionId` | BIGINT | Y | FK | 상위 섹션 |
| `order` | INT | N | IDX | 순서 |
| `templateSectionYn` | CHAR(1) | N |  | 템플릿 유래 여부 |
| `appliedTemplateVersion` | INT | Y |  | 적용 당시 버전 |

- `UNIQUE(documentId, sectionId)`.
- 삭제된 템플릿 섹션도 기존 문서에서는 조회할 수 있어야 한다.

## 3.13 `relationshipTypes`

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `ownerAdminId` | BIGINT | Y | FK | 사용자 관계 소유 ADMIN |
| `name` | VARCHAR(300) | N |  | 관계명 |
| `description` | TEXT | Y |  | 설명 |
| `systemYn` | CHAR(1) | N | IDX | 기본 관계 여부 |
| `minTargetCount` | TINYINT | N |  | 최소 대상 수 |
| `maxTargetCount` | TINYINT | N |  | 최대 대상 수 |

- `minTargetCount >= 2`, `maxTargetCount >= minTargetCount`.
- 기본 관계는 `systemYn = Y`, 소유자 NULL이며 SUPER_ADMIN만 관리한다.
- 사용자 관계는 `systemYn = N`, 소유자 ADMIN이며 소유자의 여러 프로젝트에서 재사용한다.
- 기본 관계명은 시스템 범위, 사용자 관계명은 소유 ADMIN 범위에서 유일하다.

## 3.14 `relationshipTypeRoles`

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `relationshipTypeId` | BIGINT | N | FK | 관계 유형 |
| `name` | VARCHAR(200) | N |  | 내부 역할명 |
| `displayName` | VARCHAR(300) | N |  | 표시 관계명 |
| `roleOrder` | INT | N | IDX | 역할 순서 |
| `requiredYn` | CHAR(1) | N |  | 필수 여부 |

- `UNIQUE(relationshipTypeId, roleOrder)`.
- `UNIQUE(relationshipTypeId, name)`.
- 역할 슬롯 하나에는 실제 문서 하나만 배정한다.

## 3.15 `worldRelationshipTypes`

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `worldId` | BIGINT | N | FK | 월드 |
| `relationshipTypeId` | BIGINT | N | FK | 활성 관계 |

- `UNIQUE(worldId, relationshipTypeId)`.
- 기본 관계 또는 월드 소유 ADMIN의 사용자 관계만 활성화할 수 있다.
- 역할별 카테고리가 최소 대상 조건을 충족하기 전에는 선택지에 표시하지 않는다.

## 3.16 `worldRelationshipRoleCategories`

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `worldRelationshipTypeId` | BIGINT | N | FK | 월드 관계 설정 |
| `relationshipTypeRoleId` | BIGINT | N | FK | 역할 |
| `categoryId` | BIGINT | N | FK | 허용 카테고리 |

- 세 컬럼 조합은 유일하다.
- 역할과 카테고리는 월드 관계 설정과 정합해야 한다.
- 필수 역할에는 허용 카테고리가 하나 이상 필요하다.
- 문서 경로 중 하나가 허용 카테고리와 일치하면 배정할 수 있다.

## 3.17 `documentRelationships`

하나의 실제 관계 묶음을 관리한다.

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `worldId` | BIGINT | N | FK | 월드 |
| `worldRelationshipTypeId` | BIGINT | N | FK | 사용 관계 설정 |
| `createdByAdminId` | BIGINT | N | FK | 생성 관리자 |
| `description` | TEXT | Y |  | 관계 설명 |

- 관계 설정과 관계 인스턴스는 같은 월드에 속해야 한다.
- SUB_ADMIN은 관계 기능을 관리할 수 없다.

## 3.18 `documentRelationshipTargets`

| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:---:|---|---|
| `documentRelationshipId` | BIGINT | N | FK | 관계 인스턴스 |
| `relationshipTypeRoleId` | BIGINT | N | FK | 역할 슬롯 |
| `documentId` | BIGINT | N | FK | 대상 문서 |

- `UNIQUE(documentRelationshipId, relationshipTypeRoleId)`.
- `UNIQUE(documentRelationshipId, documentId)`.
- 대상 문서는 같은 월드에 속하고 역할의 카테고리 조건을 충족해야 한다.
- 대상 수는 최소·최대 범위를 만족하고 모든 필수 역할을 채워야 한다.

## 4. 권한

| 기능 | SUPER_ADMIN | ADMIN | SUB_ADMIN |
|---|:---:|:---:|:---:|
| ADMIN 생성 | 가능 | 불가 | 불가 |
| SUB_ADMIN 생성 | 가능 | 가능 | 불가 |
| 프로젝트 관리 | 전체 | 소유 프로젝트 | 불가 |
| 월드 관리 | 전체 | 소유 프로젝트 | 불가 |
| 카테고리 관리 | 전체 | 소유 프로젝트 | 배정 프로젝트 |
| 템플릿 관리 | 전체 | 소유 프로젝트 | 배정 프로젝트 |
| 문서 관리 | 전체 | 소유 프로젝트 | 배정 프로젝트 |
| 기본 관계 관리 | 가능 | 불가 | 불가 |
| 사용자 관계 관리 | 전체 | 소유 관계 | 불가 |
| 월드 관계 설정 | 전체 | 소유 프로젝트 | 불가 |
| 실제 문서 관계 관리 | 전체 | 소유 프로젝트 | 불가 |

권한 없는 프로젝트는 목록·검색·직접 URL·API에서 존재 여부도 노출하지 않는다. 모든 하위 데이터 접근은 서버에서 프로젝트 권한까지 역추적해 검증한다.

## 5. 인증 흐름

1. SUPER_ADMIN이 ADMIN을, ADMIN이 SUB_ADMIN을 생성한다.
2. 시스템이 임시 비밀번호를 생성하고 해시만 저장한다.
3. 임시 비밀번호 원문을 계정 이메일로 한 번 발송한다.
4. 최초 로그인에는 비밀번호 변경 전용 단기 토큰만 발급한다.
5. 비밀번호 변경 전에는 다른 기능을 사용할 수 없다.
6. 변경 성공 후 정상 액세스·리프레시 JWT를 발급한다.
7. 리프레시 JWT는 HttpOnly·Secure 쿠키에 저장하고 해시를 DB에 보관한다.

## 6. 문서 처리 흐름

### 로드

1. `documents.content`를 조회한다.
2. `documentSections`와 `sections`에서 구조를 조회한다.
3. 제목·레벨·순서에 따라 Markdown을 섹션별로 분리한다.
4. 분리된 내용은 프런트엔드 임시 스토어에만 둔다.
5. 섹션 수만큼 textarea를 표시하며 제목은 수정할 수 없다.

### 저장

1. 섹션별 임시 데이터를 수집한다.
2. DB의 제목·레벨·순서를 적용해 Markdown을 재조립한다.
3. 결과 문자열을 `documents.content`에 저장한다.
4. 하위 제목이 필요하면 textarea에 제목 문법을 쓰지 않고 하위 섹션 추가 기능을 사용한다.

## 7. 후속 위키 리비전 메모

- 자동 저장은 사용하지 않는다.
- 저장 버튼을 클릭한 경우에만 판정한다.
- 현재 리비전과 제출한 Markdown이 다를 때만 신규 리비전을 생성한다.
- 리비전에는 `documents.content`만 저장한다.
- 리비전 ID는 자동 증가 PK다.
- 문서와 현재 리비전은 별도 매핑으로 관리한다.
- 복원은 현재 리비전 매핑만 변경하며 신규 리비전을 만들지 않는다.
- 복원 후 수정하여 저장하면 신규 리비전을 생성한다.
