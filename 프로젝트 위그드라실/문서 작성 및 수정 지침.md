# 문서 작성 및 수정 지침

## 1. 문서의 역할

이 `문서 작성 및 수정 지침.md`는 `프로젝트 위그드라실` 설정 저장소에서 설정 문서를 조회하고, 점검하고, 윤문하고, 보강하고, 개편하고, 병합하거나 분리하며, 신규 문서를 작성할 때 사용하는 독립 실행 지침이다.

Codex가 설정 저장소를 작업 공간으로 직접 열었을 때에는 별도의 프롬프트 폴더가 없어도 이 문서 하나만으로 작업 절차를 시작할 수 있다. 저장소 안에 `AGENTS.md`, 시리즈별 작성 지침, 템플릿이 존재하면 해당 자료를 함께 읽되, 이 문서가 규정한 점검·윤문·검증 절차는 생략하지 않는다.

이 문서는 조언 모음이 아니라 실행 규칙이다. 사용자가 점검만 요청하면 파일을 변경하지 않고 보고서를 작성하며, 수정·적용·보강·병합·재작성·신규 작성까지 요청하면 현재 작업 공간의 로컬 파일을 직접 수정하고 검증한다.

## 2. 최우선 원칙

규칙의 우선순위는 다음과 같다.

1. 현재 대화에서 사용자가 내린 최신 명시 지시
2. 현재 작업 공간의 프로젝트 루트 `AGENTS.md`
3. 대상 시리즈 또는 공통 설정 폴더의 `AGENTS.md`
4. 대상 문서군의 최신 템플릿
5. 이 독립 실행 지침
6. 현재 설정 폴더의 정본 문서와 연결 문서
7. 모델의 일반적인 추정

상위 규칙과 하위 규칙이 충돌하지 않는다면 모두 적용한다. 시리즈별 메타데이터나 문서 구조처럼 범위가 좁은 규칙은 이 문서의 일반 규칙을 구체화하는 것으로 본다.

사용자가 확정한 설정을 제안이나 가능성으로 약화하지 않는다. 반대로 미확정 자료, 소문, 학설, 설정 정비 단계의 내용을 확정 정설로 승격하지 않는다.

문서의 문체를 개선한다는 이유로 고유명사, 수치, 연대, 인과관계, 정보 공개 수준, 주장 강도, 분류와 소속을 변경하지 않는다.

## 3. 설정 저장소 판별

### 3.1 기준 루트

설정 정본의 기준 루트는 다음 폴더다.

```text
프로젝트 위그드라실
폴더 ID: 1Wjo6z5YfZDTjzfwNNVhR4ubZ2CVhH6oj
```

현재 작업 공간이 이 폴더의 로컬 복사본이나 동기화된 작업 폴더라면, 현재 파일 시스템을 기준으로 실제 구조를 확인한다.

### 3.2 직계 하위 폴더

루트의 직계 하위 폴더 중 `위그드라실`은 모든 시리즈를 포괄하는 공통 설정 허브다. 이 폴더 자체는 하나의 시리즈가 아니다.

`위그드라실`을 제외한 직계 하위 폴더는 시리즈 후보로 취급한다. 현재 확인된 시리즈는 룩스테라와 엘드로스지만, 시리즈 목록을 고정하지 말고 작업할 때마다 실제 직계 하위 폴더를 조회한다.

새로운 직계 하위 폴더에 `AGENTS.md`, `설정`, `비밀 설정` 또는 시리즈 고유 문서 구조가 존재하면 신규 시리즈로 판단할 수 있다. 구조가 불완전하면 검색 대상에서 제외하지 말고 `구조 미정`으로 보고한다.

### 3.3 하위 폴더의 기본 역할

- `설정`: 공개된 일반 설정
- `신격`: 공개된 신격·신앙·교단 자료
- `비밀 설정`: 미공개 진실과 상위 비밀
- `세력 관계`: 세력·인물·단체 사이의 관계와 공개 수준
- `스토리 설계`: 장기 플롯, 사건 설계, 공개 순서
- `설정 정비`: 문제 발견, 검토 결과, 변경 계획, 정본 적용, 검증 결과, 미해결 사항과 완료 이력을 관리하는 작업 문서군. 실제 확정 내용은 해당 정본에 반영하며, 설정 정비 문서는 정본을 대신하지 않는다.
- `템플릿`: 문서 형식과 메타데이터 기준
- `이미지`: 설정 문서가 참조하는 정식 시각 자료. 외부 생성·보관 폴더와 구분한다.
- 시리즈 고유 폴더: 해당 시리즈 `AGENTS.md`의 정의를 따른다.

모든 시리즈가 같은 하위 폴더를 가질 필요는 없다. 존재하지 않는 폴더를 추정으로 만들지 않는다.

### 3.4 공통 설정과 시리즈 설정

공통 설정은 프로젝트 전체에 적용되는 우주론, 세계 간 연결, 공통 용어, 상위 원리를 다룬다.

시리즈 설정은 해당 시리즈에서의 구체적인 역사, 지역, 인물, 제도, 발현 방식과 예외를 다룬다.

두 문서의 서술이 달라도 적용 범위가 다르면 충돌이 아니다. 같은 범위와 같은 시점의 사실이 서로 모순될 때만 정합성 문제로 판정한다.

## 4. 작업 전 필수 탐색

문서를 점검하거나 수정하기 전에 다음 순서로 자료를 읽는다.

1. 프로젝트 루트 `AGENTS.md`
2. 이 독립 실행 지침
3. 프로젝트 루트 `템플릿 구조 점검 수칙.md`
4. 대상 시리즈 또는 `위그드라실` 폴더의 `AGENTS.md`
5. 대상 문서군의 최신 템플릿
6. 직접 수정할 문서
7. 그 문서가 연결하는 상위·하위·관련 문서
8. 해당 문서를 역참조하는 문서
9. 같은 고유명사, 사건, 지역, 세력, 연대를 공유하는 문서
10. 관련 `설정 정비`, `비밀 설정`, `세력 관계`, `스토리 설계`
11. 대상 시리즈에 존재하는 관련 `인덱스`
12. 대상 시리즈의 `설정 정비/설정 정비 현황.md`와 동일 대상·고유명사·문제 유형의 기존 정비 문서

자료가 많더라도 대상 문서만 고립해서 수정하지 않는다. 설정 문서는 위키 링크, 고유명사, 지역 분류, 연대와 인과관계로 연결되므로 최소한 직접 연결 문서와 역참조 문서는 함께 확인한다.

### 4.1 권장 탐색 명령

```bash
find . -type f -name '*.md' | sort
find . -maxdepth 2 -type d | sort
rg -n --glob '*.md' '검색어'
rg -n --glob '*.md' '\[\[[^]]+\]\]'
rg -n --glob '*.md' 'title:|uuid:|docType:|type:|subtype:|region:|status:'
```

특정 문서를 병합하거나 이름을 변경할 때에는 기존 파일명과 링크 대상을 모두 검색한다.

```bash
rg -n --glob '*.md' '\[\[기존 문서명([#|][^]]*)?\]\]'
rg -n --glob '*.md' '기존 문서명'
```

### 4.2 인덱스 문서

시리즈의 `인덱스` 폴더에는 여러 정본 문서를 횡단해 비교하고 탐색하기 위한 정리 문서를 둔다. 정치 체제, 대륙별 세력, 연표처럼 동일한 사실을 여러 문서에서 확인해야 하는 작업은 관련 인덱스를 먼저 읽어 범위와 연결 대상을 파악한다. 인덱스는 새로운 정본을 대신하는 문서가 아니라, 정본의 이름·분류·핵심 차이와 직접 링크를 정렬하는 탐색 표면이다.

인덱스를 작성하거나 갱신할 때에는 연결된 정본 문서의 공개 수준과 주장 강도를 보존한다. 근거가 부족한 항목은 추정으로 메우지 않고 `보강 필요` 또는 이에 준하는 상태로 표시하며, 인덱스에서 발견한 누락·충돌은 원문 또는 설정 정비 문서에서 해결한다. 이름·분류·정치 체제·관계가 바뀌면 관련 인덱스도 함께 갱신하고, 인덱스의 링크가 실제 정본 파일을 가리키는지 검증한다.

### 4.3 템플릿 구조 점검

템플릿이 존재하는 문서를 작성·수정·개편·병합·분리하거나 구조 일치 여부를 점검할 때에는 프로젝트 루트 `템플릿 구조 점검 수칙.md`를 적용한다. 대상 시리즈의 최신 템플릿을 프론트매터 `type`·`subtype`, 시리즈 `AGENTS.md`, 문서의 실제 역할로 판정하고, 필수 상위 섹션의 이름과 순서를 비교한다.

템플릿 일치는 모든 하위 제목과 문단 수를 동일하게 만드는 작업이 아니다. 필수 `##` 구조는 유지하되 문서 고유의 독립 주제는 올바른 상위 섹션 아래에서 확장할 수 있다. 최소 두 문단 기준을 최대 두 문단으로 오해하거나, 문단 수를 맞추기 위해 제목을 추가하지 않는다. 구조를 변경할 때에는 기존 내용의 이동 대응표와 앵커 링크 영향을 함께 확인한다.

## 5. 작업 유형 판별

작업을 시작하기 전에 요청을 다음 유형 중 하나 이상으로 분류한다.

### 5.1 조회

설정 사실, 문서 위치, 연결 관계를 찾는 작업이다. 파일을 변경하지 않는다.

### 5.2 점검

구조, 메타데이터, 링크, 정합성, 연대, 공개 수준, 밀도, 문체 문제를 진단한다. 사용자가 수정까지 요청하지 않았다면 보고서만 작성한다.

### 5.3 순수 윤문

기존 의미와 정보량을 유지한 채 한국어 문장, 문단 연결, 리듬, 번역투와 기계적 표현만 다듬는다.

순수 윤문에서는 원문에 없는 인물, 사건, 장소, 제도, 사례, 해석을 추가하지 않는다. 정보가 부족해도 임의로 보강하지 않고 부족한 지점을 보고한다.

### 5.4 보강

기존 정본에 근거하여 부족한 섹션에 원인, 작동 방식, 사회적 파장, 갈등, 현재의 변화 등을 추가한다.

새 내용은 기존 정본에서 직접 도출할 수 있어야 한다. 확정 근거가 없는 내용은 `제안`, `미확정`, `추정`으로 분리하거나 작성하지 않는다.

### 5.5 개편

기존 설정을 유지하면서 섹션 구조, 정보 배치, 문서 경계를 재설계한다.

개편 전후의 정보 대응표를 만들고, 사라진 정보와 새로 추가된 정보가 없는지 확인한다.

### 5.6 재작성

문서 전체의 문장을 새로 쓰되 기존 정보와 주장 강도를 보존한다.

재작성은 순수 윤문보다 변경 범위가 크므로, 고유명사·수치·연대·인과관계·공개 수준을 별도 보존 목록으로 고정한 뒤 시작한다.

### 5.7 병합

둘 이상의 문서를 하나의 문서로 합친다.

병합 대상이 독립 개념인지, 상위 문서의 지역·하위 개념·세부 섹션인지 먼저 판단한다. 상위 문서의 내부 구성 요소에 불과하다면 별도 문서를 유지하지 않고 상위 문서의 하위 섹션으로 편입할 수 있다.

### 5.8 분리

한 문서가 서로 다른 공개 수준, 문서 유형, 시리즈 범위, 독립 개념을 과도하게 함께 다룰 때 문서를 나눈다.

분리 후에는 원본 링크를 새 문서로 갱신하고, 상위 문서에 두 문서의 관계를 설명한다.

### 5.9 신규 작성

대상 시리즈, 문서군, 저장 위치, 템플릿을 확인한 뒤 새 문서를 만든다.

기존 문서와 중복되는 개념이 있는지 먼저 검색하며, 단순 별칭이나 지역 하위 요소를 불필요하게 독립 문서로 만들지 않는다.

## 6. 로컬 파일 작업 원칙

현재 Codex 작업 공간의 로컬 파일은 사용자가 수정·적용을 요청했을 때 직접 편집할 수 있다.

외부 저장소로 업로드하거나 동기화하거나 배포하는 작업은 수행하지 않는다. 현재 작업 공간 밖의 원천을 임의로 수정하지 않는다.

사용자가 점검만 요청한 경우에는 파일을 변경하지 않는다. 수정 요청이 명확하면 변경 전 상태를 확인하고, 변경 후에는 `git diff` 또는 동등한 파일 비교로 실제 수정 내용을 검증한다.

기존 파일명은 특별한 이유가 없으면 유지한다. 이름 변경이나 삭제가 필요한 경우에는 링크 갱신과 삭제 대상 목록을 함께 처리한다.

## 7. 정본과 충돌 판정

### 7.1 적용 범위 우선 판정

서술이 다를 때에는 먼저 다음을 확인한다.

- 공통 설정과 시리즈 설정의 범위가 다른가
- 공개 기록과 실제 비밀이 다른가
- 현재 정본과 변경 예정 자료가 다른가
- 서로 다른 시대나 지역을 다루는가
- 학설, 소문, 신앙적 해석과 객관적 사실이 다른가

범위나 정보 단계가 다르면 각 문서의 역할을 유지한다.

### 7.2 실제 충돌

다음 조건을 모두 만족하면 실제 충돌로 판정한다.

- 같은 대상
- 같은 시점
- 같은 적용 범위
- 같은 정보 단계
- 양립할 수 없는 서술

실제 충돌을 발견해도 임의로 하나를 삭제하거나 섞지 않는다. 충돌 문서, 충돌 문장, 가능한 해석, 필요한 사용자 결정을 보고한다.

### 7.3 설정 정비 자료

`설정 정비`는 변경 예정 자료일 수 있다. 사용자가 해당 내용을 확정했다고 명시하지 않았다면 현재 정본을 자동으로 대체하지 않는다.

설정 정비의 내용이 이미 공개 설정에 반영되었는지 확인하고, 반영 여부가 불분명하면 중복 또는 미반영 후보로 표시한다.

후속 수정이 필요한 점검 결과, 실제 변경 내역, 검증 결과는 임시 검토 폴더나 범용 파일에 나누어 두지 않는다. 대상 시리즈의 설정 정비 현황을 확인한 뒤 기존 정비 문서를 갱신하거나 신규 작업을 등록하고, 적용 내역·검증 결과·미해결 사항·처리 이력을 같은 문서에 남긴다. 정비 문서는 정비안 작성만으로 완료 처리하지 않으며, 정본 반영·역참조·인덱스·라이브러리·메타데이터·링크 검증과 미해결 사항 분리, 중앙 현황 갱신이 끝났을 때만 완료로 처리한다.

## 9. 프론트매터와 파일 규칙

### 9.1 기본 원칙

새 설정 문서는 YAML 프론트매터를 사용한다. 기존 문서는 현재 시리즈의 규칙과 템플릿에 맞는지 확인한다.

대상 시리즈의 템플릿이 존재하면 그 필드와 선택값을 우선한다. 템플릿이 없을 때에는 아래 공통 필드를 기본값으로 사용한다.

```yaml
---
title: '문서 제목'
uuid: 'UUID v4'
docType: 'setting'
thumbnail: ''
status: '시작 전'
type: ''
subtype: ''
region: ''
created_at: ''
updated_at: ''
---
```

기존 문서를 수정할 때에는 기존 `uuid`를 유지한다. 새 문서를 작성할 때에만 새 UUID v4를 생성한다.

`thumbnail` 값이 없으면 `''`로 기록한다. 빈 메타데이터 값은 임의의 하이픈이나 설명문으로 채우지 않는다.

### 9.2 문서명과 제목

파일명과 `title`은 특별한 사유가 없으면 일치시킨다.

기존 문서를 수정할 때에는 원본 파일명을 유지한다. 이름을 바꾸어야 한다면 저장소 전체에서 기존 위키 링크를 검색하고 새 파일명으로 갱신한다.

### 9.3 문서군

일반 설정은 `docType: setting`을 사용한다. 세부 문서군은 시리즈별 지침과 템플릿을 따른다.

기본적으로 다음 문서군을 구분한다.

- `setting`: 공개 설정
- `deity`: 신격
- `secret_setting`: 비밀 설정
- `relation`: 세력 관계
- `story_design`: 스토리 설계
- `maintenance`: 설정 정비
- `template`: 템플릿

문서군을 추정으로 바꾸지 않는다. 기존 값이 현재 폴더 역할과 충돌할 때에만 수정 후보로 보고한다.

### 9.4 내부 링크

내부 연결은 현재 설정 폴더의 실제 파일명과 제목을 기준으로 한다.

```md
[[문서명]]
[[문서명#섹션명]]
[[문서명#섹션명|표시 문구]]
```

링크 대상이 존재하는지 확인한다. 파일이 이동·병합·삭제되면 모든 역참조 링크를 갱신한다.

이미지 임베드와 위키 링크는 설정 본문의 메타 표현 금지 대상이 아니다.

### 9.5 용종 이미지 참조 경로

`TRPG 데이터/14. 용종 이미지`는 생성하거나 수집한 용종 이미지를 유형별로 보관하는 작업용 저장소다. 이 폴더는 프로젝트 위그드라실 설정 문서가 사용하는 정식 이미지 경로가 아니며, 용종 문서의 프론트매터와 본문에서 직접 참조하지 않는다.

룩스테라 용종 문서의 `thumbnail`, Obsidian 이미지 임베드, Markdown 이미지 링크와 그 밖의 이미지 참조는 다음 경로를 사용한다.

```text
프로젝트 위그드라실/룩스테라/이미지/용종 도감/<파일명>
```

```yaml
thumbnail: '프로젝트 위그드라실/룩스테라/이미지/용종 도감/<파일명>'
```

```md
![[프로젝트 위그드라실/룩스테라/이미지/용종 도감/<파일명>]]
```

- `TRPG 데이터/14. 용종 이미지`, `14. 용종 이미지` 또는 그 하위 경로가 용종 문서에 남아 있으면 잘못된 참조로 판정한다.
- 보관 폴더의 이미지를 문서에 연결하려면 먼저 정식 이미지 루트에 같은 파일을 배치한다.
- 정식 이미지 루트의 실제 파일명과 확장자를 확인한다. 파일이 없으면 경로를 추정하거나 보관 폴더를 대신 참조하지 않고 누락 파일과 필요한 복사·이동 작업을 보고한다.
- 경로 점검은 프론트매터의 `thumbnail`과 본문의 모든 이미지 임베드를 함께 대상으로 한다.

## 10. 본문 구조

### 10.1 첫 섹션

첫 번째 실질 본문 섹션은 `## 개요`로 둔다.

프론트매터, 문서 제목, 대표 이미지 임베드는 `개요` 앞에 둘 수 있다. 다른 실질 설정 섹션이 `개요`보다 먼저 나오지 않게 한다.

### 10.2 섹션 구성

`개요` 이외의 섹션 제목과 순서는 문서 유형과 최신 템플릿에 맞게 정한다.

`도입`, `본론`, `상세 설명`, `결론`처럼 기능만 표시하는 제목보다 실제 설정 내용을 드러내는 제목을 사용한다.

### 10.3 항목과 요약

대상 시리즈의 `AGENTS.md` 또는 템플릿이 `항목` 섹션을 요구하면 반드시 유지한다.

기본 구조는 다음과 같다.

```md
## 항목

내용
```

`요약`이 존재하면 문서의 마지막 섹션으로 둔다. `항목`은 `요약` 바로 앞에 둔다.

```md
## 항목

내용

## 요약

...
```

`항목`과 `요약`은 실질 설정 섹션의 최소 분량 규칙에서 제외한다.

### 10.4 문단

설정 문서의 기본 단위는 설명형 문단이다.

하나의 의미 흐름을 이루는 문단 안에서 임의로 줄을 바꾸지 않는다. 의미 단위가 달라질 때에만 빈 줄을 두어 문단을 나눈다.

실질 서술 문단은 문장 수와 무관하게 최소 100토큰을 확보한다. 한 문장이 길어도 100토큰 미만이면 문단 밀도 부족이며, 여러 문장으로 썼더라도 100토큰에 못 미치면 같은 판정을 적용한다. 이 기준은 섹션 전체의 최소 2문단·300토큰 기준과 별도로 함께 충족해야 한다.

목록과 표는 계급, 구성원, 연표, 물품, 능력, 관계값처럼 탐색성이 중요한 정보를 정리할 때 사용한다. 원인, 사회적 의미, 갈등, 인식을 목록만으로 대체하지 않는다.

## 11. 세계관 내부 서술

설정 본문은 세계 안에서 성립하는 기록처럼 작성한다.

문서를 만든 사람, 문서를 사용하는 사람, 게임을 운영하는 사람의 관점이 본문과 섹션 제목에 드러나지 않게 한다.

다음과 같은 제작·운영 관점 표현은 설정 본문에서 제거하거나 세계 내부의 표현으로 바꾼다.

- 이 문서는 무엇을 정리한다
- 이 설정에서는
- 설정상
- 문서 작성 시
- 플레이어
- GM
- 세션
- 캠페인
- TRPG
- 게임 규칙
- 이미지 생성
- 시나리오 활용
- 모험 활용
- 관련 문서와 활용
- 설정 고정 문장

필요한 정보를 삭제하지 말고 세계 안의 주체와 제도로 환원한다.

- `플레이어는 이 지역에서 선택해야 한다` → `이 땅에 들어선 탐험대는 선택을 강요받는다`
- `시나리오 활용` → `현재의 분쟁과 위기`
- `NPC 묘사` → `주민의 인식과 행동`
- `설정상 금지된다` → `왕국법은 이를 금지한다`
- `독자에게 알려 준다` → `학자들의 기록에는 이 사실이 남아 있다`

학자, 부족의 전승, 교단, 국가의 법, 상인의 소문, 탐사 기록처럼 세계 안에 실제로 존재하는 관찰 주체를 사용한다.

YAML 프론트매터, 위키 링크, 이미지 임베드, 표의 필드명, 코드 블록, 파일 경로와 운영 지침 문서는 이 원칙의 직접적인 제거 대상이 아니다.

## 12. 섹션 밀도

### 12.1 목적

설정 점검의 목적은 문서를 무조건 길게 만드는 것이 아니다.

각 섹션은 해당 설정이 무엇인지, 어떻게 작동하는지, 누구에게 어떤 영향을 주는지, 어떤 갈등을 만드는지 독립적으로 설명해야 한다.

글자 수가 많아도 추상적인 문장을 반복하면 밀도가 낮다. 짧더라도 핵심 원인과 작동 방식이 분명한 문장은 가치가 있지만, 정식 설정 문서의 핵심 섹션은 충분한 맥락을 갖추어야 한다.

### 12.2 정량 기준

문서 제목으로 사용하는 `#`을 제외하고 실제 설정 내용을 구분하는 모든 Markdown 제목을 독립된 섹션으로 판정한다. `##` 아래에 `###`가 있으면 `##`와 `###`는 서로 다른 섹션이며, `####` 이하도 같은 원칙을 적용한다. 제목 단계가 낮다는 이유로 최소 분량 기준을 완화하지 않는다.

각 섹션의 직접 본문은 해당 제목 직후부터 다음 Markdown 제목이 나오기 전까지다. `##` 섹션은 첫 `###`가 나오기 전에 자체 본문만으로 기준을 충족해야 하며, `###` 아래의 본문을 상위 `##`의 문단 수나 토큰 수에 합산하지 않는다. `###` 역시 첫 `####`가 나오기 전에 같은 기준을 독립적으로 충족한다. 상위 섹션과 하위 섹션의 분량을 중복 계산하지 않는다.

신규 작성, 보강, 개편, 재작성에서는 각 실질 설정 섹션의 직접 본문을 최소 2개의 실질 서술 문단으로 구성하고 최소 300토큰 이상 확보한다. 안정적인 작성 목표는 섹션마다 320~450토큰이며, 설정의 중요도와 복합성에 따라 더 길어질 수 있다.

최소 2문단은 하한선이며 최대치가 아니다. 한 주제가 계속 이어진다면 3문단, 4문단 또는 그 이상으로 충분히 전개하며, 모든 섹션을 정확히 2문단으로 맞추지 않는다. 문단 수를 맞추기 위해 설명을 반복하거나 아직 독립되지 않은 내용을 별도 제목으로 분리하지 않는다.

제목은 문단 수를 조절하는 장치가 아니다. 독자가 별도로 탐색할 필요가 있는 독립 주제, 고유명 개념, 별도의 작동 원리·생활권·절차가 존재할 때만 하위 제목을 만든다. 같은 원인과 작동 흐름을 공유하는 내용은 하나의 섹션 안에서 여러 문단으로 연결한다.

상위 제목을 하위 제목을 묶기 위한 빈 컨테이너로만 사용하지 않는다. 하위 제목으로 내려가기 전에 상위 섹션의 정의, 범위, 작동 방식 또는 상위 맥락을 자체 문단으로 설명한다.

토큰 계산은 가능한 경우 `o200k_base`를 사용한다. 다른 기준을 사용하면 보고서에 명시한다.

다음 요소는 토큰 계산에서 제외한다.

- YAML 프론트매터
- 섹션 제목
- 대표 이미지 임베드
- `항목`
- 선택적인 `요약`
- 빈 표와 자리표시자

직접 본문 안에 있는 목록과 표의 실제 내용은 토큰 계산에 포함할 수 있지만 최소 2개의 실질 서술 문단으로 계산하지 않는다. 하위 제목 아래의 본문은 해당 하위 섹션에서만 계산하며 상위 섹션의 분량에는 포함하지 않는다. 코드 블록이나 인용문 안의 `#` 기호는 실제 Markdown 제목이 아닌 경우 섹션 경계로 판정하지 않는다.

판정 예시는 다음과 같다.

```md
## 사회 구조

상위 섹션의 첫 번째 실질 서술 문단.

상위 섹션의 두 번째 실질 서술 문단.

### 귀족 계층

하위 섹션의 첫 번째 실질 서술 문단.

하위 섹션의 두 번째 실질 서술 문단.
```

위 구조에서는 `## 사회 구조`와 `### 귀족 계층`이 각각 최소 2문단·300토큰을 충족해야 한다. 반대로 `## 사회 구조` 바로 아래에 자체 본문 없이 `### 귀족 계층`이 시작되면, 하위 섹션이 충분히 길더라도 `## 사회 구조`는 형식 미충족이다.

### 12.3 순수 윤문의 예외

사용자가 순수 윤문만 요청했다면 분량을 맞추려고 새 설정을 추가하지 않는다.

윤문 뒤 `##`, `###`, `####` 등 어느 실질 설정 제목의 직접 본문이라도 300토큰이나 2문단 기준에 미달하면 하위 섹션의 분량을 합산하거나 내용을 임의로 늘리지 말고 `밀도 보강 필요`로 보고한다.

### 12.4 구조적 예외

다음 문서는 300토큰·2문단 기준을 기계적으로 적용하지 않는다.

- 템플릿
- 메타데이터 중심 문서
- 관계값 중심의 세력 관계 문서
- 표와 단계가 핵심인 운영 문서
- 짧은 연결 문서와 색인
- 설정 정비의 체크리스트
- 사용자가 의도적으로 짧게 유지하라고 지시한 문서

예외 문서라도 설명형 문단이 존재한다면 문장 자연스러움과 의미 보존은 점검한다.

### 12.5 밀도 구성 요소

주요 섹션은 필요한 범위에서 다음 요소를 포함한다.

- 정의와 위치
- 기원과 형성 과정
- 현재의 구조와 작동 방식
- 사회·문화·생태·정치·경제적 의미
- 이해관계자와 외부 인식
- 갈등, 위험, 금기, 부작용
- 다른 설정과의 연결
- 현재 시점의 변화
- 발생 가능한 사건

모든 요소를 매번 같은 순서로 넣지 않는다. 문서 유형과 섹션의 역할에 맞는 요소만 선택한다.

### 12.6 밀도 판정

- `부족`: 1~2문장 요약에 그치며 작동 방식과 파장이 거의 없다.
- `보통`: 정의와 기능은 있지만 구체적인 장면, 사회적 긴장, 사례가 부족하다.
- `적정`: 정의, 작동 방식, 사회적 의미, 위험이 서로 연결된다.
- `우수`: 섹션 하나만 읽어도 장면, 갈등, 인물 반응, 후속 사건이 떠오른다.

## 13. 한국어 윤문 원칙

### 13.1 적용 목적

윤문의 목적은 설정의 의미와 장르를 유지하면서 번역투, 기계적인 문장 구조, 과도한 완곡 표현, 반복적인 접속사와 형식명사를 줄이는 데 있다.

문장을 화려하게 만드는 것이 목적이 아니다. 한국어 설정 문서로서 자연스럽고 직접적이며 읽기 쉬운 문장을 만든다.

### 13.2 심각도

- `S1 필수 수정`: 한 번만 나타나도 명백하게 부자연스러운 표현
- `S2 반복 시 수정`: 한두 번은 자연스러울 수 있으나 같은 문서나 섹션에서 세 번 이상 반복되면 문제
- `S3 보조 조정`: 다른 패턴과 겹쳐 기계적인 인상을 강화할 때만 조정

고유한 제도명, 법률 문구, 직접 인용, 등장인물의 말버릇은 문맥을 우선한다.

### 13.3 번역투와 피동

다음 표현을 기계적으로 반복하지 않는다.

- `~에 대하여`, `~에 대해`
- `~를 통하여`, `~를 통해`
- `~에 있어서`
- `~라는 점에서`
- `~와 관련하여`, `~와 관련된`
- `~에 기반하여`, `~을 바탕으로`
- `가지고 있다`
- `~에 의해`
- `만들어지다`, `이루어지다`
- `~에서의`, `~으로부터의`, `~에로의`, `~에의`

목적격, 주제 조사, 직접적인 동사, 실제 행위자를 사용해 문장을 구체화한다.

- `용성에 대해 연구한다` → `용성을 연구한다`
- `의식을 통해 힘을 얻는다` → `의식을 치러 힘을 얻는다`
- `특징을 가지고 있다` → `특징이 있다`
- `왕명에 의해 폐쇄되었다` → `왕명으로 폐쇄되었다`
- `동맹이 이루어졌다` → `두 국가는 동맹을 맺었다`

행위자가 미상이어야 하거나 비밀을 감추어야 하는 경우에는 피동을 유지할 수 있다.

`되어진다`, `보여진다`, `잊혀지게 된다` 같은 이중 피동은 단일 피동이나 능동문으로 고친다.

### 13.4 가능형과 주장 강도

확정된 기능을 `~할 수 있다`로 흐리지 않는다.

정본에서 확정된 규칙이라면 직접 서술한다. 실제 확률, 조건, 미확정 가능성을 뜻한다면 가능형을 유지한다.

불확실성 표현을 정리할 때에도 확실성 단계는 바꾸지 않는다.

- `가능성이 있을 수 있다` → `가능성이 있다`
- `~할 수 있을 것으로 보인다` → 문맥에 맞는 한 단계의 불확실성만 유지

### 13.5 명사 나열과 추상 주어

조사 없는 명사 연쇄를 줄인다.

- `왕국 북부 국경 방어 체계 붕괴` → `왕국 북부의 국경 방어 체계가 무너졌다`

`사건이 변화를 가져왔다`, `기록이 진실을 보여 준다`, `제도가 안정성을 제공한다`처럼 추상 주어와 만능 동사를 반복하지 않는다.

- `사건 뒤로 제도가 바뀌었다`
- `기록에서 진실이 드러난다`
- `이 제도로 국경이 안정되었다`

### 13.6 대명사

한 문단에서 `그`, `그녀`, `그것`, `그들`, 소유격이 반복되면 이름, 호칭, 집단명으로 바꾸거나 주어를 생략한다.

인물이나 장면이 바뀌는 지점에서만 주어를 다시 명시한다.

### 13.7 긴 수식

핵심 명사 앞에 관형절이 여러 겹 쌓이면 문장을 나누거나 뒤에서 설명한다.

독자가 핵심 주어와 서술어에 도달하기 어려운 문장은 구조를 단순화한다.

### 13.8 영어와 고유어

일반적인 의미를 가진 외국어는 자연스러운 한국어로 바꾼다.

세계관 고유어, 공식 명칭, 고정 약어, 어원과 암호처럼 원문 자체가 중요한 표현은 유지한다.

같은 용어의 원문과 전체 번역을 연속으로 중복하지 않는다. 원어 병기는 필요한 경우 첫 등장 한 번으로 제한한다.

### 13.9 접속사

문장마다 다음 접속사를 붙이지 않는다.

- 그리고
- 또한
- 따라서
- 즉
- 나아가
- 아울러
- 게다가
- 더욱이
- 하지만
- 그러나
- 반면

논리 관계가 문장 자체에서 드러나면 접속사를 생략한다.

앞 문장을 `이는`, `이 점에서`, `이 관점에서 보면`으로 다시 설명하지 말고 실제 결과를 직접 쓴다.

### 13.10 형식명사

다음 표현이 반복되면 직접적인 주어와 서술어로 바꾼다.

- `것이다`
- `점`, `바`, `수`, `데`
- `~라는 것`
- `~다는 뜻이다`
- `~할 필요가 있다`
- `~이 필요하다`
- `N 능력`

- `권력이 약해졌다는 뜻이다` → `권력이 약해졌다`
- `통제 능력이 있다` → `통제한다`
- `변화가 필요하다` → 어떤 세력이나 인물이 무엇을 바꾸려 하는지 서술

세계 내부의 법, 의무, 금기를 설명하는 `해야 한다`는 유지하되 누가 누구에게 요구하는지 밝힌다.

### 13.11 수식어와 명사화

다음 패턴을 반복하지 않는다.

- `매우`, `정말`, `대단히`, `극히`
- 뜻이 겹치는 이중 수식
- `역할과 기능`, `의미와 가치`, `방식과 방법`
- `~적`, `~성`, `~화`가 이어지는 명사화
- `정치적 안정성`, `사회적 영향력`, `문화적 정체성` 같은 추상어 연쇄

강도는 피해, 규모, 기간, 비교 대상으로 보여 준다.

- `효율성 강화` → `효율이 높아졌다`
- `체계 고도화` → `체계가 정교해졌다`

학술·법률 용어로 굳어진 표현은 유지한다.

### 13.12 AI 상투구

다음 표현을 습관적으로 사용하지 않는다.

- 결론적으로
- 종합하면
- 정리하자면
- `~라고 할 수 있다`
- `~에 다름 아니다`
- 매우 중요하다
- 시사하는 바가 크다
- 주목할 만하다
- 간과할 수 없다
- 크게 세 가지로 나뉜다
- 다음과 같은 특징이 있다
- 혁신적인
- 획기적인
- 전례 없는
- 압도적인
- 파격적인
- `~해야 할 때다`
- `X에서 Y로`
- `X을 넘어 Y로`

중요성을 선언하지 말고 누구에게 어떤 결과가 생기는지 설명한다.

과장어가 실제로 최초, 최대, 유일 같은 확정 사실을 뜻한다면 근거를 확인한 뒤 사용할 수 있다.

### 13.13 구조와 서식

모든 설명을 `첫째·둘째·셋째`로 나누지 않는다.

법률 조항, 의식 단계, 계급 순서, 연표처럼 순서 자체가 설정 정보일 때에는 번호 목록을 유지한다.

불릿과 표는 탐색성을 높일 때만 사용한다. 모든 문단을 동일한 정의문으로 시작하지 않으며, 헤딩 직후 `이 절에서는` 같은 안내문을 반복하지 않는다.

설정 문서 제목과 본문에 장식용 이모지, 체크 표시, 경고 아이콘을 사용하지 않는다.

모든 헤딩에 `제목: 부제` 형식을 반복하지 않는다.

### 13.14 쉼표와 문장 리듬

`~고,`, `~지만,`, `~면서,`, `~는데,` 뒤에 불필요한 쉼표를 찍지 않는다.

대부분의 문장에 쉼표가 들어가면 문장을 나누거나 어순을 조정한다.

모든 문장을 같은 길이로 맞추지 않는다. 짧은 문장과 긴 문장은 의미의 무게에 따라 달라져야 한다.

같은 종결어미가 네 문장 이상 연속되면 문장 구조와 시제를 점검한다.

일반 규칙은 단순 현재로 쓰고, 실제로 진행 중인 사건만 `~고 있다`로 쓴다.

### 13.15 완곡 표현

`~로 보인다`, `~라고 여겨진다`, `~인 것으로 판단된다`를 반복하지 않는다.

정본으로 확정된 내용은 단언한다. 학설, 소문, 추정만 불확실성을 유지한다.

`양쪽 모두`, `장점도 있지만`, `균형 잡힌 시각`, `신중한 접근`을 반복하며 판단을 피하지 않는다. 세력마다 입장이 다르면 주체와 조건을 분리해 서술한다.

### 13.16 시각적 장식

본문 전체를 굵은 글씨로 강조하지 않는다.

따옴표는 직접 인용, 별칭, 특수 용례, 논쟁적인 명칭에만 사용한다.

긴 대시와 괄호 부연을 반복하지 않는다. 중요한 설정은 괄호 밖의 본문에 편입한다.

약칭, 연도, 단위, 원어 표기는 괄호로 남길 수 있다.

## 14. 과윤문 방지

순수 윤문의 권장 변경률은 원문 대비 약 5~30%다.

30%를 넘으면 의미와 장르가 훼손되지 않았는지 다시 검토한다. 50%를 넘으면 전체 재작성보다 문제 구간만 수정하고 나머지를 원문으로 되돌리는 것을 우선한다.

보강, 개편, 재작성은 새 내용이 포함되므로 전체 변경률을 기계적으로 적용하지 않는다. 기존 문장 수정과 신규 문단 추가를 분리해 검토한다.

다음 신호 중 두 가지 이상이 나타나면 과윤문으로 판정한다.

- 백과사전·사료풍 문서가 에세이나 감상문처럼 변했다.
- 원문에 없던 비유, 수사, 감정적 평가가 추가되었다.
- 격식 있는 서술이 구어체나 해요체로 바뀌었다.
- 모든 문장이 의도적으로 짧아졌다.
- 핵심 설정 용어가 동의어로 바뀌어 문서 간 추적이 어려워졌다.
- 분량을 맞추려고 같은 의미를 다른 말로 반복했다.
- 공개 설정과 비밀 설정의 경계가 흐려졌다.

과윤문 신호가 나타나면 문제 구간을 원문과 대조하고 수정 범위를 줄인다.

같은 구간을 자동으로 재윤문하는 횟수는 최대 세 차례로 제한한다. 세 번째 수정 뒤에도 해결되지 않으면 원문을 유지하고 수동 검토 대상으로 표시한다.

## 15. 문서 유형별 점검

다음 항목은 고정된 섹션 템플릿이 아니라 확인 범위다. 실제 구조는 대상 시리즈의 최신 템플릿을 따른다.

### 15.1 대륙·지역·지형

## 16. 공개 수준 분리

공개 문서에는 세계 안에서 인물과 사회가 알 수 있는 사실을 적는다.

공식 선전, 잘못된 믿음, 학설과 소문도 공개 설정에 포함될 수 있다. 단, 그것이 객관적 진실이 아니라는 정보 단계는 유지한다.

비밀 문서에는 실제 원인, 은폐된 진실, 왜곡된 기록, 상위 연결고리를 적는다.

공개 문서와 비밀 문서가 같은 사건을 다룰 때에는 서로 다른 정보 단계가 위키 구조에서 분명히 드러나야 한다.

## 17. 연대와 인과관계

연대가 있는 문서는 사건 발생 연도와 본문 표현이 일치하는지 확인한다.

인물이 태어나기 전 사건에 참여하거나, 국가가 세워지기 전의 법을 집행하거나, 기술이 발명되기 전에 사용되는 식의 시간 오류를 찾는다.

연표는 날짜 목록만으로 끝내지 않는다. 어떤 사건이 다음 사건을 가능하게 했는지, 어느 사건이 제도와 가치관을 바꾸었는지 연결한다.

복수 시리즈가 같은 프로젝트에 속하더라도 직접 연결과 간접 연결을 구분한다. 서로 다른 세계의 역사와 물리 조건을 불필요하게 하나로 섞지 않는다.

## 19. 병합·분리·삭제 규칙

### 19.1 병합 대상 판정

다음에 해당하면 상위 문서로 병합하는 것을 검토한다.

- 상위 지역 안의 단일 하위 지역
- 하나의 개념을 설명하기 위한 세부 작동부
- 독립 문서의 대부분이 상위 문서와 중복된다.
- 독립적인 역사, 세력, 규칙, 연결망이 부족하다.
- 사용자가 하나의 문서로 관리하기를 명시했다.

### 19.2 병합 절차

1. 병합 대상 문서들의 프론트매터와 본문을 읽는다.
2. 보존 목록을 만든다.
3. 기준이 될 상위 문서를 정한다.
4. 하위 문서의 내용을 상위 문서의 적절한 `###` 또는 `####` 섹션으로 편입한다.
5. 중복 문장을 제거하되 고유 정보는 모두 보존한다.
6. 상위 문서 안에서 하위 지역의 관계와 위치를 명확히 설명한다.
7. 삭제될 문서를 참조하는 링크를 섹션 앵커로 바꾼다.
8. 삭제 대상 목록을 만든다.
9. 링크 검색과 내용 보존 감사를 수행한다.

링크 예시는 다음과 같다.

```md
[[라크샤라 대륙#용맥의 심장|용맥의 심장]]
```

### 19.3 UUID

병합 기준 문서의 UUID를 유지한다.

삭제되는 하위 문서의 UUID를 기준 문서에 복제하지 않는다. 추적이 필요하면 작업 보고서의 병합 기록에 원본 문서명과 UUID를 남긴다.

### 19.4 분리 절차

1. 분리 기준을 문서 유형, 공개 수준, 시리즈 범위, 독립 개념 중 하나로 명확히 정한다.
2. 원본 문서의 UUID는 중심 문서에 유지한다.
3. 새 문서에는 새 UUID를 부여한다.
4. 원본과 새 문서 사이에 위키 링크를 만든다.
5. 중복 설명은 최소화하고 각 문서의 책임을 분리한다.
6. 모든 역참조 링크가 올바른 문서를 가리키는지 확인한다.

### 19.5 삭제

사용자가 삭제를 요청했거나 병합으로 문서가 완전히 대체된 경우에만 로컬 파일을 삭제한다.

삭제 전에는 다음을 확인한다.

- 해당 파일만 보유한 고유 정보가 없는가
- 역참조 링크가 모두 갱신되었는가
- 이미지나 첨부 파일의 사용처가 남아 있는가
- 삭제 대상이 템플릿이나 상위 지침에서 요구되는 파일이 아닌가

## 20. 실행 절차

### 단계 1. 요청 해석

작업 유형, 대상 시리즈, 대상 문서, 수정 허용 범위를 확정한다.

명확한 지시가 있으면 불필요한 확인 질문 없이 진행한다.

### 단계 2. 저장소 구조 확인

현재 루트와 직계 하위 폴더를 확인한다.

대상 시리즈와 문서군을 판별하고, 관련 `AGENTS.md`와 템플릿을 읽는다.

### 단계 3. 문서 수집

대상 문서, 직접 연결 문서, 역참조 문서, 같은 고유명사와 연대를 공유하는 문서를 찾는다.

### 단계 4. 보존 목록 작성

고유명사, 수치, 연대, 인과관계, 주장 강도, 공개 수준, 링크 대상을 기록한다.

### 단계 5. 점검

다음 순서로 문제를 찾는다.

1. 저장 위치와 문서군
2. 프론트매터
3. 파일명과 제목
4. 내부 링크와 이미지 참조 경로
5. 공개 수준
6. 연대와 인과관계
7. 문서 경계와 중복
8. 섹션 구조
9. 섹션 밀도
10. 세계관 내부 서술
11. 한국어 윤문
12. 과윤문 위험

### 단계 6. 수정

S1 문제를 먼저 국소 수정한다.

S2 문제는 반복 횟수를 확인한 뒤 반복 구간만 수정한다.

보강이 허용된 작업에서만 정보 밀도를 높인다.

문서 구조를 바꿀 때에는 정보 대응표를 유지한다.

### 단계 7. 연결 갱신

이름 변경, 병합, 분리, 삭제가 있었다면 모든 위키 링크와 역참조를 갱신한다.

### 단계 8. 검증

원문과 수정본을 비교하고 보존 목록을 감사한다.

프론트매터, 링크, 토큰 수, 문단 수, 헤딩 순서, 공개 수준을 검사한다. 템플릿이 존재하는 문서는 `템플릿 구조 점검 수칙.md`에 따라 적용 템플릿과 필수 상위 구조의 일치 여부를 다시 확인한다.

### 단계 9. 결과 보고

수정 파일, 신규 파일, 삭제 파일, 보류 사항, 충돌 사항, 검증 결과를 요약한다.

## 21. 검증 명령 예시

### 21.1 변경 확인

```bash
git diff -- .
git status --short
```

현재 작업 공간이 버전 관리 저장소가 아니라면 `diff -u` 또는 파일 해시를 사용한다.

### 21.2 오래된 링크와 이름

```bash
rg -n --glob '*.md' '기존 문서명'
rg -n --glob '*.md' '\[\[기존 문서명([#|][^]]*)?\]\]'
```

### 21.3 기본 구조

```bash
rg -n --glob '*.md' '^## 개요$'
rg -n --glob '*.md' '^## 항목$'
rg -n --glob '*.md' '^## 요약$'
```

### 21.4 메타 표현

```bash
rg -n --glob '*.md' '이 문서는|설정상|플레이어|GM|세션|캠페인|TRPG|게임 규칙|시나리오 활용|이미지 생성'
```

검색 결과를 자동으로 전부 삭제하지 않는다. 운영 지침, 직접 인용, 세계 내부 고유 용례인지 문맥을 확인한다.

### 21.5 중복과 금지 패턴

```bash
rg -n --glob '*.md' '되어진|보여진|~에 있어서|결론적으로|종합하면|정리하자면'
```

실제 검색 패턴에서는 물결표를 제외하고 문서에 등장하는 표현을 사용한다.

### 21.6 링크 대상 검사

위키 링크에서 파일명과 섹션명을 추출하여 실제 파일과 헤딩이 존재하는지 검사한다.

링크에 표시 문구가 있으면 `|` 앞의 대상만 검증한다.

### 21.7 용종 이미지 경로

```bash
rg -n --glob '*.md' 'TRPG 데이터/14\. 용종 이미지|14\. 용종 이미지'
rg -n --glob '*.md' '프로젝트 위그드라실/룩스테라/이미지/용종 도감/'
find '룩스테라/이미지/용종 도감' -type f | sort
```

첫 번째 검색은 결과가 없어야 한다. 두 번째 검색에서 찾은 `thumbnail`과 이미지 임베드의 파일명·확장자가 세 번째 명령의 실제 파일 목록과 일치하는지 대조한다.

## 22. 점검 보고 형식

### 전체 판정

문서 전체의 구조, 정합성, 밀도, 문체와 수정 우선도를 간단히 정리한다.

### 문서별 점검

각 문서의 강점과 핵심 문제를 적는다. 문제가 있는 섹션은 섹션명을 표시한다.

### 구조 및 메타데이터

프론트매터, 파일명, 제목, 문서군, 저장 위치, `개요·항목·요약` 구조를 기록한다.

### 링크 및 정합성

깨진 링크, 역참조, 중복 문서, 연대 오류, 용어 충돌, 분류 충돌을 기록한다.

### 섹션 밀도

섹션별 문단 수와 토큰 수를 표시한다. 정량 기준 충족 여부와 `부족·보통·적정·우수` 판정을 함께 적는다.

### 문체 및 윤문

발견한 S1·S2·S3 패턴, 수정 여부, 대표 수정 전후 예시를 기록한다.

### 내용 보존 감사

고유명사, 수치, 연대, 인과관계, 주장 강도, 공개 수준, 직접 인용과 링크가 유지되었는지 기록한다.

### 과윤문 및 장르 보존

에세이화, 문학화, 구어화, 과도한 문장 길이 조작, 핵심 용어 교체가 없는지 기록한다.

### 변경 파일

- 수정 파일
- 신규 파일
- 이름 변경 파일
- 병합 파일
- 삭제 파일
- 수정하지 않고 보류한 파일

### 보류와 사용자 판단

충돌을 임의로 해결할 수 없거나 설정 근거가 부족한 항목을 분리한다.

## 23. 완료 판정

다음 질문에 모두 답할 수 있어야 작업 완료로 판정한다.

- 대상 시리즈와 문서군을 올바르게 판별했는가?
- 실제 저장소 구조와 템플릿을 확인했는가?
- 첫 실질 본문 섹션이 `개요`인가?
- 파일명과 `title`이 의도대로 일치하는가?
- 기존 UUID와 고유명사가 보존되었는가?
- `##`, `###`, `####` 등 모든 실질 설정 제목을 각각 독립 섹션으로 판정했는가?
- 각 섹션이 다음 제목으로 넘어가기 전에 직접 본문만으로 최소 2개의 실질 서술 문단과 최소 300토큰을 충족하는가?
- 최소 2문단을 최대 2문단으로 오해하여 모든 섹션을 정확히 두 문단으로 제한하거나, 문단 수를 맞추기 위해 불필요한 하위 제목을 만들지 않았는가?
- 하위 섹션의 문단과 토큰을 상위 섹션에 중복 합산하지 않았는가?
- 순수 윤문 작업에서 새 설정을 임의로 추가하지 않았는가?
- 세계관 바깥의 제작·운영 표현이 설정 본문에 남아 있지 않은가?
- 공개 설정과 비밀 설정이 섞이지 않았는가?
- 설정 정비와 현재 정본을 혼동하지 않았는가?
- 연대와 인과관계가 연결 문서와 일치하는가?
- 내부 링크가 실제 파일명과 섹션을 가리키는가?
- 룩스테라 용종 문서의 `thumbnail`과 모든 이미지 임베드가 `프로젝트 위그드라실/룩스테라/이미지/용종 도감/<파일명>`을 사용하는가?
- 용종 문서에 `TRPG 데이터/14. 용종 이미지`, `14. 용종 이미지` 또는 그 하위 경로가 남아 있지 않은가?
- 참조한 이미지 파일이 정식 이미지 루트에 실제로 존재하는가?
- 병합·분리·이름 변경 뒤 역참조가 갱신되었는가?
- 번역투와 기계적 반복을 줄였는가?
- 주장 강도와 불확실성 단계가 유지되었는가?
- 과윤문으로 장르와 문서 성격이 바뀌지 않았는가?
- 원문에 있던 정보가 누락되지 않았는가?
- 원문에 없던 사실이 확정 설정으로 추가되지 않았는가?
- 수정 결과를 실제 diff와 검색 명령으로 검증했는가?
- 변경 파일과 보류 사항을 사용자에게 명확히 보고했는가?

하나라도 확인할 수 없다면 작업을 완료했다고 단정하지 않는다.

## 24. Codex용 최종 실행 계약

Codex는 설정 문서 작업을 받을 때 다음 계약을 따른다.

1. 먼저 현재 설정 저장소의 실제 구조를 읽는다.
2. 대상 시리즈와 문서군을 판별한다.
3. 관련 지침, 템플릿, 연결 문서를 읽는다.
4. 수정 전에 보존 목록을 만든다.
5. 사용자가 허용한 작업 범위 안에서만 파일을 변경한다.
6. 문체 개선과 설정 보강을 구분한다.
7. 정본에 없는 내용을 임의로 확정하지 않는다.
8. 병합·분리·이름 변경 시 전체 역참조를 갱신한다.
9. 수정 후 실제 명령으로 결과를 검증한다.
10. 검증하지 않은 상태에서 완료를 선언하지 않는다.

이 문서는 설정 저장소에서 독립적으로 실행할 수 있는 완결된 기준이다. 다른 프롬프트 문서를 읽지 못하더라도 이 절차를 기준으로 작업하며, 현재 저장소의 시리즈별 지침과 템플릿이 존재하면 그 구체적인 메타데이터 규칙을 추가 적용한다.
